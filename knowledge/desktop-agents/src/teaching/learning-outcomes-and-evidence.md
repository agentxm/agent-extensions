# Learning outcomes and evidence

Each outcome states what a learner can **do**. Reading a page or completing a
video is participation, not evidence of the outcome.

## Desktop Agent 101

| ID | Learner can | Required evidence |
| --- | --- | --- |
| 101.1 | Distinguish chat, a saved project, and a desktop agent for a given task | Sort at least six varied tasks and explain two choices |
| 101.2 | Select a useful, low-risk first task | Task choice names value, visible output, reversibility, and excluded risks |
| 101.3 | Give an agent a bounded assignment | Brief states goal, allowed sources, protected items, output, checks, and pause points |
| 101.4 | Review a plan and permission request | Learner narrows or rejects an intentionally overbroad action |
| 101.5 | Verify a result and actual changes | Check note traces sampled claims to sources and identifies all changed items |
| 101.6 | Transfer the basic loop to day-to-day work | Independent brief, output, and check note from a new task |

## Desktop Agent 102

| ID | Learner can | Required evidence |
| --- | --- | --- |
| 102.1 | Identify work worth turning into a reusable method | Two observations separate stable steps from changing inputs |
| 102.2 | Describe a reusable workflow | Workflow card covers trigger, inputs, steps, output, checks, limits, and owner |
| 102.3 | Inspect shared instructions before adoption | Review identifies source, access, included files, requirements, checks, and unsafe behavior |
| 102.4 | Test transfer and failure behavior | Results from ordinary, changed, incomplete, and unsafe cases |
| 102.5 | Decide whether and how to share | Decision uses observed evidence and names audience, limits, and next review |

## Desktop Agent 201

| ID | Learner can | Required evidence |
| --- | --- | --- |
| 201.1 | Recognize when informal reuse needs management | Diagnosis connects observed pain to discovery, source, version, dependency, or retirement needs |
| 201.2 | Establish a trusted main copy and owner | Management plan names source, owner, origin, version, and change history |
| 201.3 | State requirements and supported settings | Requirement record names inputs, tools, access, companion parts, and settings actually tested |
| 201.4 | Plan safe updates and retirement | Release plan includes comparison tests, communication, rollback, replacement, and disable path |
| 201.5 | Design a product-neutral operating model | Capstone lets another person find, obtain, test, update, and stop the workflow |

## Cross-level safety outcome

At every level, the learner keeps private and high-stakes information inside
approved boundaries, leaves outside effects behind explicit human approval,
and seeks qualified review where consequences require it. A critical safety
miss cannot be offset by a strong content score.

Activities, practice, and assessment should use the same outcome IDs. A
derivative course may omit an outcome only when it states the reduced promise.
